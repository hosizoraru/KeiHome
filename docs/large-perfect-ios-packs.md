# 完美图标 iOS 完整包的导入与本地应用

## 两个实际阻断点

HyperOS Phone AVD 已下载的 iOS 样式完整生成包约 618 MiB，包含 2490 个生成条目、
2467 个去重后的映射。首次生成用时 251674 ms。它暴露了两个独立问题：

1. 生成器允许 1 GiB 包，但 App 导入、系统侧接收、转换结果及主题授权读取仍有
   256 MiB 上限。原始 ZIP 会先被拒绝，后续任意一处旧上限也会阻断应用确认。
2. 动态日历使用系统时钟广播、短暂刷新的帧率控制器、星期图片和 `Time format="dd"`。
   这是合法的本地视觉程序，但此前分层校验器没有覆盖，出现导入成功而本地应用
   确认不可用的情况。

修复按体积预算和程序结构生效，不依赖 iOS 文件名、包名或某个桌面版本。

## 预算与验证边界

`IconPackBudgets` 统一定义 1 GiB 输入、2 GiB 解压总量、4 GiB 本地导入归档配额。
这些是上限，不预分配相应内存或空间。复制、CRC 和摘要校验使用有界流。
单条目 96 MiB、十万个条目、路径检查、压缩比和 XML 等限制继续保留。
生成器、普通 ZIP 导入、系统中转、转换确认及主题读取应一起修改，避免只放开
最前一层而产生后续的“已导入但不可应用”。

`LocalCalendarLayerProgram` 只承认日期和星期的完整本地图片、四种系统时钟广播，
以及已声明的、暂停启动且不循环的帧率控制器。控制点必须按时间递增、最多 60 秒、
不超过 120 fps，并以零帧率结束。命令只能播放本场景声明的控制器。
外部 URI、数据提供器、设置读取、其他广播、缺失图片及未知命令继续拒绝。
普通时钟可使用空的广播容器；这不意味着接受任意绑定节点。

## 避免重复生成

同配置输出使用源内容、选项、变换版本、渲染能力和掩模构成的指纹。
成功生成后在独立缓存目录保存归档 SHA-256，最多保留 64 个证明。
再次生成时校验完整文件摘要，匹配才复用成品，跳过重复的深色渲染和 ZIP 写入；
文件变动、证明缺失、源或配置变化则重新生成。修改渲染算法时仍须迭代对应
`REVISION` / `LAYER_CONTRACT`。

证明计入缓存并随缓存清理删除，不放在生成 ZIP 目录或分层渲染缓存目录。
这保持了“仅保留最新生成包”和手动管理 ZIP 的边界，也避免证明无限累积。

## 可复用验收

JVM 可以显式指定本地归档，执行完整的本地程序验证：

```bash
KEIHOME_LOCAL_ICON_ARCHIVE=/absolute/path/to/icons.zip ./gradlew \
  :app:testDebugUnitTest --tests '*LocalIconArchiveFixtureTest'
```

AVD 仪器测试使用 `realImportMatrix=1` 才会进行真实导入。
附加 `perfectStyle=iOS` 时生成完整 iOS 样式并只验收该产物。
如已取得生成证据，可用 `existingPerfectArchive=perfect-<hash>-<hash>.zip`
复用私有生成目录中现有的完整归档；报告明确记录复用，不能当作重新生成。
其他包的扫描只是上下文，不应把单个样式的结果报告成整个矩阵通过。

原始归档校验、系统导入回执、转换后本地应用确认和系统主题的实际应用按钮是
不同验收层，必须分别保留结果。真实应用后还应核对系统图标文件、来源标记、
桌面截图并恢复原主题；仅出现“已导入”不代表应用验收完成。
