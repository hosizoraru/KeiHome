# HyperOS Phone AVD system stall, 2026-11-08

## Scope and result

Investigation target: `emulator-5580`, HyperOS Phone, launcher 8593.
No APK installation, module disabling, native reload, device reboot, or
forced process restart was performed during this investigation.
The physical phone was not used.

This was a system-level incident, not merely an unsuccessful UI screenshot.
DropBox records a real `system_server_watchdog` on November 8 at 09:19:48.
The terminal message is:

> Blocked in handler on foreground thread (android.fg) for 83s

The triggering defect is not uniquely identified. Evidence supports prolonged
system lock contention and scheduler pressure; it does not establish a
permanent Java deadlock or prove that KeiHome caused the incident.

## What the stacks establish

- Historical `system_server` main thread waits for an
  `AccessibilityManagerService` monitor. SystemUI's main thread waits in the
  corresponding accessibility window-registration Binder transaction.
- UiAutomation connection/registration also times out. Android UI automation
  depends on the same accessibility service, so repeated hierarchy dumps and
  instrumentation are unreliable while that service is blocked.
- The full Watchdog dump shows `android.fg` waiting for the AMS monitor, with
  several Binder workers queued on AMS / window-management locks.
- CPU PSI `some avg10` is 74.66% in the launcher ANR and 91.60% in the Watchdog.
  This measures time with runnable work waiting for CPU; it is neither
  application CPU usage nor a standalone explanation of the initiating fault.
- The Watchdog snapshot shows `KeiHomeIconRefresh`, `KeiHomeSystemResources`,
  and `KeiHomeAppLabel` waiting in their handler message queues. It does not
  show those threads holding the blocking service monitor.
- Some stack dumps took tens of seconds, including approximately 50.9 seconds
  for a thread in the Watchdog collection and 227.8 seconds in an earlier
  system trace. Lock owners can change during collection; these are not
  atomic snapshots from which a reliable cyclic lock graph can be inferred.
- One earlier main-thread stack includes an obfuscated module receiver-cleanup
  frame. An available sibling KeiMi mapping is consistent with
  `UserUnlockGate`, but the exact installed binary/mapping identity has not
  been authenticated. This is a lead, not attribution to either module.
- Host load and allocated swap were also substantial when inspected later.
  A later host snapshot cannot establish the host's state at the onset or
  prove that host memory pressure caused the guest fault.

The Android framework's shared accessibility-service implementation can be
checked in [AOSP AccessibilityManagerService](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AccessibilityManagerService.java).
The Xiaomi implementation and installed module interactions require separate
evidence; AOSP source is architectural context, not proof of an OEM defect.

## Handling the next recurrence

1. Stop further APK replacement, hot reload requests, hierarchy automation,
   and instrumentation when system-service queries or UiAutomation time out.
   A failed framework query is not evidence that an icon or mapping failed.
2. Preserve guest boot ID, PID/start identities, DropBox Watchdog/ANR entries,
   LSPosed logs and a bounded system log before attempting recovery.
3. Avoid repeated full thread dumps while the guest is saturated; the existing
   dumps already demonstrate that collection can be extremely expensive.
4. To identify the initiating fault, use a bounded system trace and
   authenticated module mappings, then compare one module/runtime change at
   a time. Do not infer causation by disabling several modules and rebooting
   together, or by comparing different boots as though their PIDs persisted.
5. Resume automated acceptance only after system-service responsiveness and
   ordinary UI interactions have been verified. A recovered Home screenshot
   is necessary but insufficient.
