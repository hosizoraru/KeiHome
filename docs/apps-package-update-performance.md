# 应用更新后的列表性能与下拉刷新

## 问题与证据

在 KeiHome 保持前台、进程不变时覆盖安装另一个 APK，可以重现应用列表
在刷新结束后持续变慢的问题。重启应用会暂时恢复，因此仅测启动、第一次加载
或切换筛选不足以覆盖这个场景。

基线是 `1.11.0+g2059984.b0520` 的签名 Release/R8 包，HyperOS Phone AVD
桌面为 9258。更新的是独立的测试 APK，未运行 instrumentation，KeiHome PID
在更新前、更新后与等待稳定后的三轮录制中均为 `31199`。

每轮 Perfetto 录制 16 秒，输入相同的 12 次上下交替滑动：

| 阶段 | 主线程 CPU 累计 | Recomposer 重组累计墙钟时间 |
| --- | ---: | ---: |
| 更新前 | 702.4 ms | 86.5 ms |
| 更新后 | 1541.4 ms | 1098.2 ms |
| 更新结束后再次滚动 | 1526.7 ms | 1021.4 ms |

simpleperf 使用 AVD 支持的 `cpu-clock` 事件采样主线程。结合该 APK 的 R8
mapping，约 57% 的采样时间落在 `IconPackEntry.equals` 和
`IconPackComponent.equals`。调用链来自 Compose `changed` 对
`IconPacksPage` 中目录列表的比较。

这些结果说明基线存在持续的额外主线程开销。AVD 的 Vulkan、刷新率与宿主负载
会影响绝对帧率；不能把这里的毫秒数当作实体机帧率承诺。

## 为什么刷新后会一直重复比较

目录刷新会产生内容相等的新快照。`remember(state.packs)` 判断新旧键相等时，
保留旧键与旧计算结果。之后每次重组仍需比较新列表与旧列表，其比较会深入
每个图标包、图标映射及组件。同一个快照反复使用时没有这个成本，所以重启后
表现正常；刷新后又可能出现。

主页面 Pager 会保留相邻页面，不能假设当前显示应用列表时，图标包页面完全不再
参与重组。把目录切换成隐藏状态也不足以解决键的比较成本。

目录等不可变大快照现在通过 `SnapshotIdentity` 作为 Compose 的计算键：
相同实例保留计算结果，替换实例只重新计算一次。应用列表的数据集、图标蒙版选择、
完美图标预览及 Apple 当前主题预览中相同的重键也采用这一方式。
图标包首页不计算仅子列表需要的目录筛选和排序。

这里改变的是 UI 计算键，不是图标包的业务相等定义。快照发布后不能就地修改；
新内容必须发布新实例。小的筛选参数仍按值比较。

## 更新事件与缓存

PackageManager 广播与 LauncherApps 回调需要保留包名及用户信息，合并一次更新
的多条通知。新通知不应取消已经进行的有效扫描，再为相同批次启动另一轮。

普通应用更新只失效相关用户和包名的应用预览与资源检测缓存。只有已安装图标包
自身改变时，才失效对应的图标包索引；隐藏目录保留待刷新标记，进入时再加载。
显式刷新与系统配置、覆盖资源变化仍需保留全量校验能力。

应用标签、资源检测结果等没有改变时，保留已有能力列表实例，让可见列表及滚动
位置继续使用；受影响应用的图标缓存独立失效，不能因为复用列表而显示旧图标。

## 下拉刷新与验收

拥挤工具栏中的刷新迁移到 MIUIX 原生 `PullToRefresh`。下拉动作沿用该页原有的
读取操作，不隐式生成、下载或应用图标包。刷新状态需在手势回调中及时抬起，
完成或失败后收回；避免和列表已有 overscroll、顶栏连接重复消费手势。

完整验收需使用 Release/R8，在同一进程内比较更新前、一次和连续多次后台更新后、
刷新结束后的持续滚动，并单独覆盖显式图标包目录刷新后返回应用列表的场景。
组件测试验证大目录替换后不会在后续重组中遍历映射，以及新快照和筛选条件仍生效。
